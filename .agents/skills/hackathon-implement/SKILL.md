# Hackathon Implement

依頼された範囲を、共有Specと実装が一致して動作を確認できるところまで進める。
作業順序は状況から選ぶ。固定フロー、他スキルの必須呼び出し、形式的な承認待ちは設けない。

## 実装の基準

- 関連Spec、コード、プロジェクトの指示を読み、目的と受け入れ条件を把握する。
- 最新のユーザー要求を優先し、古いSpecとの矛盾は関連箇所を更新して解消する。
- Specがなければ、依頼から目的と観測可能な受け入れ条件を短く共有文書に残す。
- 新規Specは `specs/<feature>/spec.md` を使う。既存の保存場所や形式があれば従う。
- 依頼外の機能追加や大規模な整理は行わず、目的を満たすまとまりで実装する。
- Specへの署名、承認ハッシュ、詳細なタスク分割がないことだけで作業を止めない。

## 判断とSpecの更新

- 調べられる事実は確認し、可逆な細部は既存の慣習と最小の実装から判断する。
- API、データ、画面の動作など、他の担当に影響する設計の具体化はSpecにも反映する。
- 実装中のSpec編集を許可する。重要な仮定・変更理由を短く残す。
- ユーザーの目的や受け入れ条件を、実装の都合で削除・弱体化しない。
- 根拠なく目的を選ぶ必要がある場合や、未承認の破壊・費用・公開・権限変更は確認する。
- 確認が必要な部分だけ保留し、独立した作業は続ける。決定済みの事項は再確認しない。
- 「急いで」「実装優先」が求められた範囲では、実装を先行し変更のまとまりごとにSpecを同期してよい。

## 実装と検証

- 既存の設計を活かし、対象機能の画面・API・保存など必要な接続を完成させる。
- 受け入れ条件と変更のリスクに応じ、テスト・ビルド・実動作確認を選ぶ。
- 主要な利用経路と、その変更で壊れやすい失敗経路を確かめる。
- 検証は変更箇所から始め、影響が広い場合だけ範囲を広げる。無関係な全件検査を必須にしない。
- テストは意味のある振る舞いを確認するために追加し、実装をなぞるだけのテストは増やさない。
- デモ用代替が依頼範囲に含まれる場合は、代替箇所と未接続の範囲をSpecと報告に明記する。
- テスト用の差し替えや代替動作の成功を、実サービスとの接続成功として扱わない。
- 既存のアプリ・コンテナ・ブラウザを再利用し、並行作業は編集範囲と共有資源の競合を避ける。

## 完了の判断

- 見つけた問題は依頼範囲内で修正し、変更に影響する確認を行う。
- 同じ失敗を新しい根拠なしに繰り返さず、原因・不足情報・進められる範囲を明示する。
- 共有Spec、実装、実際に確認した結果の矛盾を解消する。
- 実行できない検証は未検証として残す。未実装や既存の失敗も区別する。
- 最後に変更内容、検証結果、残っている制約を短く伝える。
- 一部しか動いていない状態を全体の完了として報告しない。
