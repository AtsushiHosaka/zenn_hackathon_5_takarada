# Hackathon Spec

細部はAIが設計し、出戻りの大きい未決事項だけ確認する。固定フローや全項目の承認は不要。

## 仕様の根拠

- `docs/project.md` のGoogle Docs URLと読み取り方針を確認する。Docsは要求のSSOT。
- 関連する本文・タブを接続済みツールで読み、部分取得を全文確認と扱わない。
- URL未設定・取得失敗なら依頼文や提供資料を暫定の根拠にし、Docs未確認と明記する。
- 文書に書かれていない事実を補わない。不足が目的や主要動作を左右する場合だけ質問する。
- 過去プロジェクトの説明を現行構成に転用せず、関連コード・既存資料を確認する。

## ローカルSpec

- 既存の保存場所を使う。新規なら `specs/<feature>/spec.md` にまとめる。
- DocsのURL・該当箇所・取得日時を残し、要求の全文コピーや第二の正本を作らない。
- 目的、対象範囲、対象外、期待する振る舞い、観測可能な受け入れ条件を残す。
- 実装判断に影響する失敗時・空状態・権限などの条件を具体化する。
- データ、API、画面、外部連携は担当間の認識合わせに必要な粒度で書く。
- AIの仮定・提案・Docsへの追記案は確定した要求と分ける。Docsは依頼なく書き換えない。
- 必要な情報を行数のために削らない。約50行の目安はスキル本文にだけ適用する。

## 自律的な判断

- 可逆な設計は、既存の慣習と最小の実装で目的を満たす案を採用する。
- 文言・配置・内部構造ごとに質問しない。重要な採用理由だけ記録する。
- 根拠から選べない目的の分岐や、未承認の破壊・費用・公開・権限変更は確認する。
- 質問には推奨案と影響を添え、回答に依存しない作業は続ける。
- 明示されたユーザーの変更は反映し、Docsと違う場合はDocs未反映と記す。

## API契約と検証の方針

- backendのAPI契約はrswag定義が生成元。詳細は `.claude/docs/backend.md` を参照する。
- iOSとの接続に必要なAPI契約は早く具体化し、未実装のAPIを利用可能と表現しない。
- フロント・backend・infraとも新規テストを前提にしない。TDDや網羅的なテスト計画は作らない。
- Swagger生成に必要な最小rswag定義は維持する。受け入れ条件とテストコードの新設は別に考える。

## 更新と成果物

- 実装で判明した細部と重要な判断は更新し、古い記述との矛盾を解消する。
- 実装の都合で要求を削らず、不具合・未実装・要求変更を区別する。
- Docsとの未反映差分を残し、ローカル編集だけでSSOT同期済みと報告しない。
- 最後にSpecの場所、主な変更、重要な仮定、未決事項を短く伝える。
- 仕様や計画だけの依頼なら、共有したところで終える。
