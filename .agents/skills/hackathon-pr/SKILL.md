# Hackathon PR

変更の目的、仕様や接続への影響、確認結果が短く伝わるPRを作る。固定のSDD工程は要求しない。

## 変更と投稿先

- git status、現在のブランチ、差分、remote、既存PRを確認する。
- ユーザーの無関係な変更は含めず、依頼範囲のファイルだけをコミットする。
- 作業ブランチがあれば再利用する。必要な新規ブランチは `codex/` を既定とする。
- ベースはユーザー指定またはリポジトリの既定ブランチ。forkでは投稿先repoも確認する。
- 同じ変更のopen PRがあれば更新し、重複PRを作らない。
- PR作成依頼は対象変更のコミット・push・PR投稿を含む。形式的な再承認は求めない。

## テンプレートに沿う本文

- `.github/pull_request_template.md` を読む。複数テンプレートなら変更に合うものを選ぶ。
- 別配置ならリポジトリ内のテンプレートを探す。見つからなければ未配置と伝え、簡潔な本文にする。
- テンプレートの見出しを保ち、案内コメントは実際の内容へ置き換える。非該当は「なし」とする。
- 問題と変更後の動作を先に書き、タイトルも最終的な差分に合わせる。
- `docs/project.md` と関連Specを確認し、該当する出典・Docs未反映差分だけを記す。
- API・DB・環境変数・iOS接続への影響は該当時に記載し、秘密情報は載せない。
- 検証結果は実行済み・未実施・失敗を区別する。CI待ちを成功と書かない。
- 新規テストの追加やカバレッジ目標をPRの条件にしない。TDDは行わない。

## 既存の検証との整合

- 変更に関係する既存チェックを選び、文書だけならアプリを起動する必要はない。
- API変更は最小rswag定義と `make docs` の生成物を含める。生成物だけを直接修正しない。
- backend CIはRSpec・Swagger再生成差分・RuboCop。既存チェックの無効化で通さない。
- iOS変更は `make ios-build` 等。ダミー動作やビルドを実API接続の証拠と扱わない。
- infra変更はshell構文・Terraformのfmt/validateなどを選び、AWS操作をPR作成の前提にしない。
- 必要な確認を実行できなければ理由と未検証範囲を記載する。重大な未達がある場合はdraftにする。

## 投稿と報告

- 差分と秘密情報の混入を確認し、通常のpushを使う。force pushやmainへの直接pushはしない。
- 本文は一時ファイルに書き、`gh pr create` / `gh pr edit` の `--body-file` で渡す。
- 作成・更新後にURL、ベース、head、本文を読み返し、CIの現時点の状態を確認する。
- 新しい変更がなければ不要なコミットやCIの再実行はしない。
- PR作成依頼にマージ・デプロイは含まれない。このrepoはmainのCI成功後に自動デプロイされる。
- CodexのPR添付ツールが使える場合は、作成・更新したPRを現在のタスクに添付する。
- 最後にPRリンクと、失敗・未検証・ユーザーの対応が必要な事項だけを短く伝える。
