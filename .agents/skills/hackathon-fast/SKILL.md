# Hackathon Fast

変更するのは作業の順序。要求の共有と、実際に動いたかの区別は残す。

## 適用範囲

- 速度を求められた作業に適用し、無関係な次の依頼へ持ち越さない。
- `docs/project.md` に従いGoogle Docsと関連Specから、今回の範囲と成功条件を把握する。
- Docs未設定・取得不能なら依頼文や提供資料を使い、未確認と記す。
- Specの整形、詳細設計書、レビュー往復、形式的な承認を実装の開始条件にしない。
- 調査や計画だけの依頼を、実装まで勝手に広げない。
- 速度を理由に要求を削ったり、実連携を無断でデモ用代替へ置き換えたりしない。

## 自律的な判断

- 可逆な細部は既存実装と慣習から決め、最短で利用経路を通す。
- 重要な仮定だけ記録し、細部ごとの選択肢提示や承認待ちは省く。
- 調べられる事実は確認する。目的の大きな分岐や未承認の破壊・費用・公開・権限変更は質問する。
- 質問には推奨案と影響を添え、依存しない作業は続ける。
- 既存資源を再利用し、並行作業によるファイルやサービスへの競合を避ける。

## Specの追従

- 機能や動作変更がまとまるごとにローカルSpecを更新する。新規は `specs/<feature>/spec.md`。
- 目的、範囲、受け入れ条件、重要な設計判断を残し、行数のために必要な情報を削らない。
- Docsの出典と未反映差分を残す。ローカル更新をDocs更新と扱わず、Docsは勝手に編集しない。
- 不具合・未実装・要求変更を区別し、実装できなかった要求を不要だったことにしない。
- 許可されたデモ用代替は境界と実連携の未検証を明記する。既存のiOSダミーも実API成功ではない。
- 中断時も実装との重要な差分と残作業を残す。

## 既存の自動化を活かす

- フロント・backend・infraとも新規テストは原則書かず、TDDはしない。追加は必要性が合意された場合だけ。
- 既存CI・テストを維持し、変更に関係する既存チェック・ビルド・実動作確認を選ぶ。
- API変更は `.claude/docs/backend.md` に従い、Swagger生成に必要な最小rswag定義だけ追加・更新する。
- `make docs` の生成物も変更に含める。Swaggerの直接編集や、生成成功を実動作成功とする報告はしない。
- backendは対象RSpecまたは `make test` とRuboCop、iOSは `make ios-build` を変更に応じて使う。
- infraはshell構文・Terraformのfmt/validateを確認し、検証の名目でAWSの構築・破棄を行わない。
- 新規E2E基盤、網羅的ケース、形式的な証跡作成を増やさない。既存request specはiOS通しのE2Eではない。
- 同じ失敗を根拠なく繰り返さず、不足する前提や別の手段を示す。

## 終了時

- 実装とローカルSpecを整え、Docs未反映・確認済み・未検証・未実装を区別する。
- 変更と残課題を短く伝え、未達がある場合は全体の完了を宣言しない。
