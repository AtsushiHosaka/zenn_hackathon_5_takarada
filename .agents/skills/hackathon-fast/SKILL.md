# Hackathon Fast

要求を共有したまま、実装を先に進めて手戻りを小さくする。
変更するのはSpec整備と実装の順序であり、ユーザーの目的や完了の意味ではない。

## 適用範囲

- ユーザーが速度や実装先行を求めた作業に適用する。無関係な次の依頼には持ち越さない。
- 既存のユーザー要求とSpecから、今回動かす範囲と成功条件を把握する。
- Specの整形、詳細な設計書、レビューの往復、形式的な承認を実装の開始条件にしない。
- Specがなくても要求が十分なら進める。目的が判断できない場合だけ先に確認する。
- 「急いで」だけを理由に、求められた機能を無断で削ったりデモ用代替に置き換えたりしない。
- 今回の依頼が調査や計画だけなら、速度を求められても実装まで範囲を広げない。

## 自律的に進める判断

- 可逆な細部は既存の実装と慣習から決め、最短で利用経路を通せる案を選ぶ。
- 重要な仮定だけ短く残す。細部ごとの選択肢提示や承認待ちは省く。
- 根拠のない事実を補わず、調べられることは必要な範囲で調べる。
- 目的の大きな分岐や、未承認のデータ破壊・費用・公開範囲・権限に関わる選択は確認する。
- 質問には推奨案と影響を添え、依存しない作業を進める。
- 既存資源を再利用し、独立した並行作業でも同じファイルやサービスへの競合を避ける。

## Specを追従させる基準

- ひとつの機能や動作変更がまとまるごとに、関連Specを更新する。
- 新規なら `specs/<feature>/spec.md` に残す。既存Specがあればその構造を維持する。
- 目的、範囲、受け入れ条件、重要な設計判断を残し、必要な情報を行数のために削らない。
- 実装で決めた細部は反映し、元の要求との差分は不具合・未実装・要求変更に分けて扱う。
- 実装できなかった要求を、最初から不要だったことにしない。
- 要求変更の権限がない差分は未達として残し、解消するか判断を求める。
- デモ用代替が依頼範囲に含まれる場合は、代替の境界と実連携の未検証を明記する。
- 作業を中断する場合も、実装との重要な差分と残作業を共有文書に残す。

## 速度を落とさず確認すること

- 主要な受け入れ条件と変更のリスクに直結する確認を優先する。
- 変更に適したテスト・ビルド・実動作確認を選び、重大な失敗経路も確かめる。
- 無関係な網羅検査や形式的な証跡作成は必須にしない。
- 失敗した検証を成功に見せたり、動作しない箇所を隠したりしない。
- 根拠が増えない試行は繰り返さず、別の手段か不足している前提を示す。

## 終了時

- 実装とSpecを同期し、確認済み・未検証・未実装を区別して伝える。
- 残った制約と次に必要な作業を短く示し、未達がある場合は全体の完了を宣言しない。
