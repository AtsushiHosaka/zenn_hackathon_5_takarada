# 日本向けEC商品を既存家具モデルと組み合わせる

日本向け家具ECから要望に合う実商品を検索し、事前に用意した3Dモデルを選ぶ。商品画像から代表色を抽出し、モデルの主素材に反映する。画像の色が取れない場合は色名から近似し、従来の素材テクスチャ生成も使う。商品そのものの3D形状は生成しない。

## 根拠と実装状況

2026年10月5日の依頼を根拠とする。ユーザー指定は、日本向けの家具量販店ECを中心に調査すること、IKEAを候補に含めること、実商品と既存モデルを組み合わせてテクスチャだけを画像生成することである。

Google Docs URLは`docs/project.md`に未設定。Docsの本文・タブは未確認で、確認日時と該当箇所も記録できない。このファイルは依頼を具体化した暫定の実装メモであり、共有Docsとの同期は未実施。

既存の[コーデ提案Spec](../room-coordination/spec.md)の候補取得境界を維持し、実EC検索・公式ページ確認・大型家具の追加と入れ替え・モデル照合・テクスチャ生成・Web描画を接続した。Google検索と画像生成はVertex AIの既存認証、または設定済みのDeveloper APIを使う。ユーザーごとの利用許可も既存Gemini設定に従う。

EC取得先はIKEA・ニトリ・LOWYA・無印良品・Francfranc の日本向け公式ドメインと、Yahoo!ショッピングの商品詳細（`store.shopping.yahoo.co.jp/<ストア>/<商品コード>.html`）に限定する。店舗ごとにページ形式と取得成否は異なる。IKEAの商品詳細から価格と寸法を取得できた。ニトリの確認ページはタイムアウト、LOWYAの確認ページは必要情報がなく、候補から除外した。検索対応ドメインの全商品を取得できるとは扱わない。

2026年10月5日の提案により、Yahoo!ショッピングとFrancfrancを追加した。Yahoo!は出店ストアが多く推し活グッズも扱い、ニトリも出店している（nitori-netストア）。Francfrancは色・デザインのある雑貨が多い。

- ニトリ公式（nitori-net.jp）は1ページ約10秒かかり、取得の読み取り上限8秒を超えるため、新しい検索候補から外し、Yahoo!のnitori-netストアで探す。保存済みの公式URLの再確認は従来どおり取得を試みる。
- Yahoo!の商品ページは価格を「価格 999 円」と表示し「税込」の語がない。価格は総額表示（税込）が義務のため、Yahoo!に限りJSON-LDの円価格を税込として扱い、`price_source`にその根拠を書く。商品番号はストアごとなので`provider_product_id`は`<ストア>/<商品コード>`とし、店名はパンくずのストア名（例: ニトリ Yahoo!店）を表示する。
- Yahoo!はJSON-LDに寸法がなく、説明文の「サイズ(約)：幅43×奥行43×高さ16cm」をGeminiのHTML抽出で読む。Francfrancは仕様表の`W795×D795×H630(SH:380)mm`をそのまま解析し、Geminiを使わない。
- 楽天市場は商品ページの直接取得が遅いため対象外とし、使う場合は公式API（アプリID登録が必要）にする。

推し活・飾り物の商品も実EC検索の候補にする。既存の3Dモデル（`acrylic_stand_case`、`oshi_goods`、`display_case`、`tapestry`、`neon`、`wall_shelf`、`vase`、`candle`）があるカテゴリに限り、商品名から次の枠へ割り当てる。

| 商品名の例 | カテゴリ | 枠 | 3Dモデル |
| --- | --- | --- | --- |
| アクスタケース、アクリルコレクションケース | acrylic_stand_case | desk_top | acrylic_stand_case |
| コレクションケース、フィギュアケース、ガラスケース | display_case | display | display_case / display_rack_open / cabinet_glass |
| うちわスタンド、アクスタ台座・ひな壇 | oshi_goods | desk_top | uchiwa_stand / acrylic_stand |
| 缶バッジディスプレイ（壁掛けは wall_decor） | oshi_goods | desk_top | badge_display |
| タペストリー、ネオンサイン、ウォールシェルフ | tapestry / neon / wall_shelf | wall_decor | 同名 |
| 花瓶、キャンドル | vase / candle | display / desk_top | vase_tulip・dried_flowers / candle |

- 高さ50cm以上のアクリルケースはコレクションケース（display）、45cm未満のコレクションケースはアクリルケース（desk_top）に読み替える。
- 「アクスタケース」の名で売られる持ち運び用のポーチ・バインダー・スマホケース・ペンケースは、部屋に飾る商品ではないため除外する。
- 3Dモデルは既存の規則どおり、寸法が2軸以上わかる商品だけ縦横比で選ぶ。ネオンサイン・タペストリーなど薄いものは、厚みを除いた面の比で比べる。
- 推し活・飾り物（上の表のカテゴリ）は、寸法がわからない軸をカテゴリの標準寸法で補い、商品名から絞った3Dモデルのうち縦横比が最も近いものを付ける。標準寸法は推定にすぎないため、比の上限では外さない。照合理由の`estimated_axes`に補った軸を残す。Yahoo!の商品ページは寸法を載せないことが多く、大きさのばらつきが小さい小物は簡易形状より実物に近く見えるため。他のカテゴリは従来どおり、寸法が推定だけなら簡易形状で表示する。
- 2026年10月6日にYahoo!ショッピングの実商品18点で確認した。カテゴリ・価格・店名は全件取得でき、3Dモデルは寸法がわかった9点に付き、8点を実際の部屋（ベッド・デスク・本棚あり）の想定位置に置けた。
- 同日、寸法を空にした推し活・飾り物10例（うちわスタンド、缶バッジディスプレイ、アクスタ台座、アクスタケース、コレクションケース、タペストリー、ネオンサイン、ウォールシェルフ、花瓶、キャンドル）で、すべて名前どおりの3Dモデルが付くことを確認した。対象外のラグは従来どおり付かない。

## 大型家具の配置・入れ替えも対象にする

対象は日本向け販売ページ、日本語の商品情報、円建て価格とする。IKEA、ニトリ、LOWYA、無印良品などの候補は[EC調査](research.md)に記す。検索候補であることと、自動取得・画像利用の許可があることは区別する。

商品検索、条件での絞り込み、モデル照合、テクスチャ生成、結果画面での表示、商品詳細への購入導線を扱う。決済・注文、海外商品、実行時の画像からの3D生成は対象外。

同日の追加回答により、ソファ・机・ベッドなどの大型家具の配置・入れ替えも対象にする。現行の配置処理は`bed_cover / curtain / rug / wall_decor / light / display / cushion / desk_top`の8枠なので、床に置く家具の配置と交換対象の指定を追加する。現行枠で置けない商品を、枠を偽って追加しない。

## 実商品を確認してから選び、配置後に生成する

Google Search groundingの出典リンクを解決して公式商品詳細URLを探し、公開ページの構造化データと商品情報から価格・寸法を確認する。検索の出典リンクを優先し、AI本文のURLは未検証の候補としてだけ扱う。公式の商品詳細ページで確認できるまで採用しない。検索出力の数値は採用しない。取得先のrobots.txt、公開IP、HTTPS、転送先を検証し、非公開APIは使わない。検索専用の既定モデルは`gemini-3.5-flash`で、URL発見には`MINIMAL`の推論量を使い、検索指示を短くする。希望に明示された用途と無関係な商品は検索しない。商品選定は既存の`GEMINI_MODEL`を使う。画像生成の既定モデルは`gemini-3.1-flash-image`。

1. 要望、予算、必要な配置枠から、カテゴリ・色・素材・形状を含む日本語の検索条件を作る。特定のテーマ3種類だけには固定しない。
2. 許可と接続方法を確認したECごとの取得処理、または検索サービスで、対象ドメインに絞って商品を探す。公式APIや提供フィードがあれば優先する。非公開APIを前提にしない。
3. 検索結果から商品詳細ページを確認し、商品・色・サイズのバリエーションを特定する。検索結果URLや検索スニペットだけでは購入候補を確定しない。
4. 構造化データを優先し、不足時は取得した公式HTMLをGeminiへ送り、主商品の価格・寸法・素材・色を抽出する。価格の引用を取得HTMLと照合し、寸法が不明な軸はカテゴリの標準寸法で補う。公式値と推定値を分け、同一店舗・商品・バリエーションの重複を除く。
5. 多数の候補を`CoordinationPlanner`へ渡し、テンプレートの要望文、部屋、保持家具、素材・色・形と合計予算に合う採用一式・代替順位をGeminiに選ばせる。大型家具は追加・交換の操作ごとに選ぶ。取得済み内部IDだけを認め、合計予算と配置可否はRubyで最終判定する。
6. 実際に配置する商品だけを既存モデルと照合する。採用できるモデルがなければ簡易形状で表示し、近似であることを示す。
7. 採用商品と素材ごとにテクスチャ画像を生成・保存し、結果のSceneへ素材の上書き情報を付ける。全検索候補の画像を生成しない。
8. 3D上の追加商品と購入リストを同じ商品IDで対応させる。生成画像による近似プレビュー、取得時の参考価格、公式の商品詳細を表示する。

## 商品データは出典とバリエーションを持つ

既存の`InteriorLinks.client.search(prompt:, theme:, slots:, max_price:)`は候補取得境界として維持する。配置やテクスチャ生成をEC取得クラスへ混ぜない。大型家具には床配置枠`floor`と操作別の候補グループを加えた。既存8枠の意味は維持する。

現行の選定処理は各枠につき1商品なので、大型家具は追加操作・用途・交換元IDごとに候補グループを分ける。同じ床配置でもソファの追加と机の入れ替えなど、複数の商品を一つの予算内で選べるようにする。候補グループの識別子は配置枠と分け、選定・配置・結果まで引き継ぐ。

`InteriorLinks::Item`の既存フィールドを基準に、次の情報を保持する。

| 情報 | 扱い |
| --- | --- |
| 内部`id` | 既存APIとGeminiの契約に合わせた正の整数。同じ商品・バリエーションで安定させる |
| `provider / provider_product_id / variant_id` | 店舗とEC側の商品・色・サイズを特定する文字列。内部IDとは分ける |
| `name / category / slot` | 実商品名、用途、配置枠。対象枠がない場合は配置候補へ渡さない |
| `price / currency / price_checked_at` | 確認した税込円価格と取得日時。送料込みとは表示しない。送料が判明した場合は別に保持する |
| `url / source_url` | 公式の商品詳細URLと情報の出典。同じバリエーションへ購入者が移動できること |
| `image_url / material / color / shape` | 取得した画像URLと素材・色・形状の根拠。画像の存在と利用許可を区別する |
| `size / size_source / estimated_axes` | 幅・高さ・奥行きをmに統一。公式値と推定値、推定した軸を分ける |
| `availability / fetched_at` | 在庫確認結果と取得日時。不明を在庫ありに変換しない |
| `image_usage` | 表示、保存、生成入力について、それぞれの許可確認結果と根拠を保持する |

追加のユーザー指示により、寸法の多少のばらつきと欠損を許容する。取得HTMLをGeminiで解釈し、取得値をmへ換算する。不明・異常な軸はカテゴリの標準寸法で補い、取得値は`size`のnull、推定軸は`estimated_axes`、プレビュー値と補完理由は`size_source`へ保存する。推定値でも配置候補に残すが、実寸での設置保証とは扱わず、画面と配置注記で購入前の確認を伝える。

商品価格合計は予算内とする。送料が不明な場合は「商品価格の合計・送料別」であることを示し、支払総額が予算内とは断定しない。価格・在庫が取得後に変わる可能性を踏まえ、購入時の確認先は公式ページとする。

## 入れ替え先を指定し、残す家具を動かさない

大型家具の操作は「追加」と「入れ替え」を区別する。入れ替えでは、解析Sceneにある既存家具IDを指定する。「活かす」対象は入れ替え対象にできず、選択の矛盾は入力時に示す。活かす対象から外しただけで、自動的に購入・入れ替えへ進めない。

現行の`kept_object_ids: []`は全家具を残す意味なので、入れ替え対応では明示的な家具操作リスト`furniture_operations`を使う。各既存家具IDについて「残す」「入れ替える」「外す」のいずれかを一つ指定し、残すIDはそのリストから導く。操作リスト未指定の旧クライアントは従来の意味を維持する。指定した場合は全部の家具を入れ替え対象にでき、残す家具を1点以上とする制限を適用しない。不明ID・重複・指定漏れと、旧選択との矛盾は拒否する。

入れ替え候補は元の用途を満たす商品から選ぶ。位置と回転は元家具の値を初期候補とし、新商品の寸法で再検証する。収まらない場合は、残す家具の位置・回転を維持したまま別の場所を検討する。配置できる候補がなければ入れ替えを成立させず、元家具を残して理由を表示する。元のBeforeのSceneは変更しない。

追加家具は床の空き領域へ置く。部屋の境界と、残す家具・採用済み商品の占有範囲に対して、幅・奥行きと回転を考慮して配置を判定する。ラグと家具、カバーとベッドなど意図した重なりは、既存の取り付け関係または明示した組み合わせに限る。別の家具への取り付けがある商品は、交換先の寸法で取り付け可否を再検証し、外れた家具IDへ取り付けたまま返さない。

扉の開閉域や必要な通路幅が現行入力から分からない場合は、部屋の外形と家具の占有範囲で確認した配置であることを示す。通行・開閉まで保証したと表示しない。完成案での位置・回転は既存の配置編集で調整でき、再提案時には手動編集済みの配置を引き継ぐ。実EC商品の寸法は手動編集値で縮めず、商品寸法で配置を判定する。カバーとカーテンも公式の幅・長さを維持し、取り付け先を覆えない商品は採用しない。カーテンの枚数が未確認なら幅を推定で倍にしない。

Sceneでは既存家具と追加商品の区別を維持し、入れ替え商品に`replaces_object_id`を持たせる。一つの既存家具を複数商品で同時に置き換えない。入れ替え成立時はAfterから元家具を除き、新商品だけを購入リストへ載せる。入れ替え失敗時は元家具をAfterに残し、失敗した候補は購入リストへ載せない。

## モデルは用途と形状で照合し、商品別に保存する

既存の明示対応があれば優先する。対応がない新しい実商品については、有効なカタログモデルの用途・形状・バリエーションを候補にし、外形比率と構造を比較する。カテゴリ一致だけで、円形ラグへ長方形モデル、片側カウチへ逆側モデルなどを割り当てない。

照合結果にはモデルID、商品バリエーション、採用理由、近似かどうかを持たせる。採用した結果は商品IDとの明示対応として保存し、表示のたびにカテゴリから選び直さない。`FurnitureModelBinding`の`managed_by`で台帳とEC照合を分け、`match_metadata`へ理由を保存する。台帳取り込みはEC照合の対応を削除しない。

商品の公式寸法とモデルの制作寸法は分ける。描画時の寸法調整はモデルの適合方式に従い、`contain`ではモデルの外形が商品寸法と完全には一致しないことを扱う。現行Webは一律`contain`相当なので、商品寸法と描画の外形を一致させる方式は未実装である。位置・回転・活かす家具とBeforeのSceneは変更しない。

## 生成するのは素材の画像だけ

木目・織り目・柄などを、正面から見た継ぎ目のない平面画像として生成する。背景、家具の輪郭、文字・ロゴ、商品写真の照明や影を焼き込まない。モデルのメッシュと元GLBは共用し、商品別に上書き情報だけを持たせる。

商品写真を生成入力に使う場合は、その利用が許可された画像に限る。表示・保存・生成入力のどれが認められるかをECごとに確認する。画像URLを読めることや検索APIを使えることだけでは、生成入力に使えるとは判断しない。

画像を生成サービスへ送る許可が未確認の場合は、根拠のある色・素材の説明を生成入力とする。2026年10月8日の依頼により、商品写真をサーバーのメモリ上で解析し、代表色を取る処理を追加した。写真は生成サービスへ送らず、保存もしない。代表色だけの表示を「生成素材」や「商品画像の再現」とは表示しない。生成サービスの利用条件・料金は選定時に確認する。

### 商品画像の代表色を低コストでモデルへ反映する

2026年10月8日の依頼を根拠とする。EC商品の色が3Dモデルに反映されないため、HTML掲載の商品画像から近似色を取り、ローポリ表示に使う。速度を優先し、画像からの色抽出にAIの追加呼び出しを使わない。この変更はGoogle Docsに未反映で、URL未設定のため本文も未確認。

対象バリエーションのJSON-LD画像を優先し、画像がない場合や取得先が未対応の場合は`og:image`または`twitter:image`を使う。画像オブジェクト形式と相対URLも扱う。確認済み画像CDNのHTTP表記はHTTPSへ直す。ページ内の関連商品や別色の画像を色抽出用に探し回らない。

取得先は実ページで確認したIKEA・ニトリ・Francfranc・Yahoo!ショッピングの画像ホストと商品画像パスに限定する。公開IPを確認して接続先を固定し、リダイレクト先も再確認する。画像はJPEG・PNG・WebP、最大2MiB、通信全体4秒、再試行なしとする。LOWYA・無印良品の画像取得先は未確認のため、従来色へ戻す。ニトリは許可済みだが今回の実画像取得はタイムアウトした。

画像は最大96×96pxに縮小する。画像の縁の色がそろう場合は、縁につながる近い色を背景として除く。透明部分を除き、中央を少し重く評価して色別の画素数を集計し、最多の色群の平均を`color`へ入れる。`product_metadata.color_source`と`image_color`に方式・画像URL・成否を残す。取得失敗、画像破損、前景不足では色名による近似へ戻す。同じ画像の成功結果は24時間、失敗は10分間、既存のRailsキャッシュに保持する。

抽出色はモデルの`tint`を優先し、ない場合は`wood`などモデル台帳にある主素材へ`material_overrides`で渡す。公式素材説明に木部の塗装の根拠があり、色名が単色の場合は`wood`にも同じ抽出色を適用する。多色商品、塗装の根拠がない木部、透明・クリア・無色仕上げは、この追加適用の対象にしない。既存家具・他商品が共有するGLBや素材は変更しない。`light`を変える場合は発光色も合わせる。色抽出が成功した商品は追加のテクスチャ生成を省く。柄・複数素材の色・室内写真からの正確な商品領域分離は今回実装せず、単色の近似として表示する。

受け入れ条件は、商品画像由来の色がGLBの主素材と簡易形状に届くこと、色抽出失敗でも商品候補を失わないこと、色抽出成功時に画像生成を呼ばないこと、共有素材や既存家具を変えないことである。保存済みのコーデには遡って反映せず、新たに生成した実ECコーデから適用する。

実確認ではIKEAのGLADOM白テーブルが`#f7f6f5`、Francfrancのグレーのフロアチェアが`#d0d0d1`になった。Yahoo!掲載の多色柄カーテンは地の色に近い`#cecec9`で、柄は再現しない。保存した実商品HTMLからのパースと画像取得・抽出は約0.2〜1.1秒。人工画像では白背景を除いて青`#2864aa`を取得し、キャッシュ再利用と破損画像のフォールバックを確認した。モデルの`tint / wood`への色適用、画像生成の省略、入力データの保持も確認した。既存APIテスト9件、関連Ruby lint、Web lint・ビルドは成功。公開環境へのデプロイと実ECコーデ生成から画面表示までの通し確認は未実施。

同日の追加確認では、現在のコードで公式商品ページと画像を取得し、IKEA PS 2026ブルーチェアが`#0b4c93`、Francfrancのピンク座椅子が`#d9b6a9`になった。商品台帳から手動で選んだ公開GLBを、Webの本番用素材適用helperで実際に描画した。最初の表示では青い椅子の木部が元色のまま残ったため、上記の塗装木部への追加適用を修正し、再描画して確認した。木部を含む青色表示とピンク色表示、元の共有素材の保持、未塗装・多色木部の追加適用除外を確認した。商品ページ取得を含む再確認は約1.4〜1.8秒。[比較画像と確認範囲](../../docs/screenshots/ec-product-color/README.md)を保存した。画像取得・色抽出・素材適用・実GLB描画の限定統合確認であり、モデル自動照合・検索AI・DB保存・コーデ生成APIの通し成功とは扱わない。既存APIテスト9件は塗装木部の補正前に実行した。補正後は関連Ruby lintと上述の実描画・条件分岐を確認した。現在の起動環境は別worktreeを参照し、Gemini認証とDBが利用できないため、通し確認は未実施。

素材名はモデルAPIの`materials`を参照し、`tint / wood / metal / leaf / pot`など必要な部位だけを変更する。未知の素材名は適用せず、テクスチャを貼らない部位の色を維持する。商品別・素材別の複製を使い、同じGLBを使う他の商品へ変更が伝わらないようにする。

既存UVの1UV=1mに合わせ、テクスチャの繰り返し幅を`tile_size_m`で指定する。モデルの表示スケールも考慮し、商品サイズが変わっても柄の実寸が意図せず変わらないようにする。Webの適用helperは表示スケールを受け取り、繰り返し量を調整する。非等方の寸法調整を使う場合は、UVまたは面ごとの繰り返し量も調整する。

生成結果は、商品バリエーション・素材・参照内容・生成設定・生成方式の版をキーに再利用する。柄の実寸は別に保持する。既存の`MODELS_BUCKET`の`textures/description-seamless-v1/`へ保存し、公開配信とCORSを再利用する。APIの新規書き込み権限はこの接頭辞だけに限定する。開発環境はローカル保存と開発限定の画像配信APIを使う。既存GLBは変更しない。

## APIと画面の契約

既存のコーデ生成ジョブからEC取得・モデル照合・生成処理を呼ぶ。新しい商品検索HTTP APIは設けない。`POST /api/v1/rooms/:id/coordinations`に次の入力を加えた。

- `furniture_operations`: 既存家具IDと`keep / replace / remove`の組。指定時は全既存家具を一度ずつ含める。空配列・未指定は旧クライアントの選択を維持する。
- `additions`: `sofa / bed / desk / chair / shelf / table`から追加する用途を選ぶ。最大6点で、同じ用途を複数指定できる。

残す家具が0点でも操作リストで指定できる。不明ID・重複・指定漏れ・旧選択との矛盾は422とする。配置する各操作に別のScene IDを付け、同じ商品を2点採用した場合も独立して扱う。

`GET /api/v1/coordinations/:id`は商品メタデータ、`product_source`、Google検索の`search_entry_points`を返す。SceneObjectには`replaces_object_id / model_size / model_fit / model_match / material_overrides / texture_status / texture_source`を加えた。Swagger生成元とWebの生成型・応答変換・保存データ検証・描画も更新した。

```json
{
  "model_match": { "model_id": 1, "reason": "用途・形状・外形比率から照合", "approximate": true },
  "texture_status": "ready",
  "texture_source": "description",
  "material_overrides": {
    "tint": {
      "texture_url": "https://<配信先>/textures/description-seamless-v1/<生成結果>.png",
      "tile_size_m": 0.5
    }
  }
}
```

テクスチャ状態は`disabled / ready / failed / skipped / unmatched`で区別する。旧Sceneも表示できる。Webは既存家具の残す・入れ替える・外す指定と追加用途を入力でき、再提案時にも引き継ぐ。検索の出典HTMLはスクリプトを許可しないiframeに表示する。

処理上限は、EC取得全体120秒、画像生成全体90秒・最大3回、コーデ生成ジョブ全体240秒。nginxは260秒、コーデPOSTは270秒、画面の完了待ちは360秒とする。本番inlineジョブではPOSTが処理を待つため、各期限を段階的に長くした。画像生成は失敗した試行も回数に含める。

モデルやテクスチャの取得失敗では単色・簡易形状で表示し、未反映を伝える。モデル未照合は汎用GLBへ補完しない（推し活・飾り物の寸法補完は上記の例外）。手動の色変更は既存のプレビュー操作として扱い、実商品の販売色を変更したと表示しない。

## 空状態と失敗の扱い

| 条件 | 振る舞い |
| --- | --- |
| 検索成功・該当商品なし | 商品が見つからない条件を示し、条件を緩めるか再検索できるようにする |
| 一部ECのタイムアウト・制限 | 取得できた候補を使い、取得できなかった店舗を記録する |
| 全ECの取得失敗 | 検索失敗を示す。該当商品なしやモック成功として返さない |
| 商品ページが削除・売り切れ | 候補から除外する。取得結果が古い場合は取得日時を示す |
| 税込価格が確認不能 | 候補から除外し、欠損理由を残す |
| 寸法の一部または全部が不明 | 標準寸法を明示した近似プレビューとして候補に残す |
| HTMLがJavaScriptの起動用ページだけで主商品情報がない | HTML抽出でも価格を確認できないため除外する。描画後の取得は未実装 |
| 大型家具の配置・入れ替えが成立しない | 不成立の理由を示す。入れ替え元は残し、不成立の商品は購入リストへ載せない |
| モデル候補なし・GLB取得失敗 | 商品情報を残し、簡易形状で表示する |
| 画像入力の許可未確認 | 商品画像を生成入力へ送らず、説明からの生成案または単色表示を使う |
| 生成失敗・時間切れ・画像取得失敗 | 商品・モデル・配置を維持し、単色表示とテクスチャ未反映を示す |

取得対象は確認したECと画像配信元に限定する。検索結果の任意URLを無制限に取得せず、ページ取得と生成の時間・候補数・再試行回数に上限を設ける。検索は用途を1〜2個ずつに分けて最大6リクエストを並列実行し（用途が3個未満なら3リクエスト）、各最大12件・合計最大36URLを集める。1回の検索に複数の用途をまとめると、一部の用途しか探されず候補が偏ったため（2026年10月7日、8用途を3検索に分けた場合に候補が4用途にとどまった）。単一用途でも店舗・価格帯・素材が異なる候補を探す。検索1リクエストは再試行込み65秒とし、応答途中の切断・接続リセットなど一時的な通信エラーは残り時間が25秒以上あれば1回だけ再試行する（並列6検索の実測が16〜54秒で、45秒では打ち切られていたため）。Googleの出典解決は最大72URI・8並列・全体12秒、商品取得とHTML抽出は6並列でEC全体120秒以内とする。商品ページ4MiB・1HTTP15秒、HTML抽出入力120KB・1抽出25秒を上限とし、公式EC商品詳細以外の移動先を取得しない。

## 観測可能な受け入れ条件

- 日本向け対象ECから、根拠を確認できる実商品の詳細URL・価格・バリエーションを返す。検索結果URLやダミー価格を実商品として扱わない。
- 要望に合う商品を選び、商品価格合計を予算内に収める。配置商品と購入リストの商品IDが一致する。
- HTML抽出で商品情報を補い、寸法不明の商品も推定軸を明示した近似配置として提案する。価格・商品名の引用は取得HTMLに存在することを確認する。
- 多用途・多店舗・価格帯を分けた検索から最大36URLを扱い、テンプレート・素材・色と合計予算に合う採用一式を選ぶ。最安商品で各枠を埋めるだけの選定は実ECでは使わない。
- ソファ・机・ベッドなどを追加・入れ替えでき、残す家具を動かさず、新商品の回転と寸法で配置を検証する。入れ替えが成立したAfterだけに新商品を置き、Beforeは維持する。
- 同じ床配置でも用途・操作ごとに複数商品を採用できる。家具が1点だけの部屋でも、その家具の入れ替えを指定できる。
- 入れ替えが成立しない場合は元家具を残し、不成立の商品を購入リストへ載せない。取り付け対象が消えた商品もそのまま返さない。
- 既存モデルから用途・形状に合うモデルを選び、照合理由を追跡できる。新しい家具形状を生成しない。
- 素材ごとに生成画像を貼り、同じモデルを使う他商品、活かす家具、BeforeのSceneへ変更が伝わらない。
- 商品画像の生成入力について確認した根拠を残す。説明だけから生成した結果は画像参照による再現として表示しない。
- 検索の空結果・失敗、モデル未対応、生成・読み込み失敗を区別し、商品情報と配置を保って表示できる。

検証は実ECの取得例、既存のbackend・Web検証、実画面での描画確認を使う。新規テストやTDDは前提にせず、API変更時の最小rswag定義のみ更新する。
