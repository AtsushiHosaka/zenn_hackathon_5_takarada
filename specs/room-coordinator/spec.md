# 提供されたデザインで写真から理想の部屋を検討するWebフロント

一人暮らしの部屋を、今ある家具を活かしながら推し活やボタニカルな空間へ変える。写真と希望を入力し、提案された部屋を3Dで見て、追加する商品の購入先を確認する。画面の基準は、ユーザーが提供したHTMLと6画面のPNGとする。

畳数・形・写真から部屋を解析し、残す家具と入れ替える家具、追加する用途、希望・予算を入力する。既存Geminiの接続設定とownerの利用許可があれば実EC検索・AI選定・素材テクスチャ生成を使い、未設定時はモックで動く。家具の3D形状は既存モデルを使う。

2026年10月5日の追加要求は、日本向けECの実商品検索と大型家具の追加・入れ替え、既存モデルへの生成テクスチャの適用である。詳細は[EC家具Spec](../ec-furniture/spec.md)を参照する。以下の「活かす家具を1点以上」「全解除は送信しない」は現行API向けの制限で、入れ替え対応では明示的な家具操作リストを使い、残す家具がない指定も可能にする。これらの追加はAPI・Webへ実装した。最新の接続確認と制限はEC家具Specを参照する。

## 受け入れ条件

- 現在の正式APIでは3〜30畳、`square`・`standard`・`long`の形と希望・予算を入力できる。希望は500文字以内、予算は1円以上の整数とする。
- 部屋の解析後、解析Sceneの既存家具から活かす家具を選び、そのIDを商品提案APIへ送る。初期状態は全選択とし、家具がある場合は1点以上を選ぶ。
- 紫の推し活・ボタニカル・韓国風のテーマをモックで選び、予算と配置場所に収まる商品を提案する。同じ部屋へ追加指示を送れる。
- 写真3〜4枚と自然言語の希望からのAI解析・生成は将来の実装対象とする。写真入力の`legacy`アダプターはJPEG・PNG・WebP、1枚10MB以内を扱うが、現在の正式APIへは写真を送らない。
- 部屋を回転・拡大し、家具を選ぶと対応する商品を確認できる。
- 家具の移動・回転、家具と壁のプレビュー色、視点、寸法表示を手動で調整し、履歴を戻す・やり直すことができる。
- 配置編集中は10cmの格子を表示し、家具を左ボタンでドラッグするとマス目に沿って動く。高さ・向き・サイズを維持し、立体・真上ではX/Z方向、正面ではX方向へ移動する。編集した配置を商品提案と再生成へ引き継ぐ。詳細は [家具配置の仕様](../furniture-layout/spec.md) を参照する。背景と通常画面のドラッグは視点の回転とする。
- 編集は明示操作でブラウザに保存し、追加商品の購入リストをCSVで保存できる。
- 部屋全体と個別家具のモデルURLを扱う。モデルがない家具は寸法と座標から表示する。
- 商品リンクと参考価格を表示し、既存家具と追加アイテムを区別する。
- 画面はRepositoryの型に依存し、送信先・フィールド名・応答形式の変更を通信層で扱う。
- 未公開APIを利用可能と表示しない。APIの失敗は明示し、サンプルへ自動で切り替えない。

## 初期表示から同じThree.jsの部屋を操作する

結果画面は初期表示から実際のThree.jsを使う。紫の結果サンプルは `referenceRoomModel.ts` で参照画像の形状と面色をモデル化し、正投影カメラで表示する。番号や家具の選択から商品情報を確認でき、ドラッグ、ホイール、回転・拡大のボタンで同じ3Dを操作する。視点のリセットも3Dカメラの操作として扱う。

窓とフレームの描画面には4mm・8mmの深度差を付け、重なる面の表示競合を解消した。植物などの細部は近似で、完全なピクセル一致は未確認。家具モデルがないAPI結果は座標・寸法から簡易形状を組み立てる。スクリーンショットは参照画像の転載ではなく、実際に動いているアプリを撮影する。

## 家具の配置・色を右側のパネルで編集する

右上のアカウントメニューの「家具の配置・色を編集」で、商品パネルの位置に編集パネルを開く。提供デザインのフォントと配色を使い、編集パネルを閉じた通常画面の構成は維持する。

今ある家具と追加家具を選び、X方向・Z方向に10cmずつ移動、15度・90度ずつ回転する。家具と壁はそれぞれ5色からプレビュー色を選ぶ。商品サイズは変えず、幅・高さ・奥行きをcmで表示し、選択した家具の寸法表示を切り替える。商品本来の色や寸法は購入先で確認する。視点は立体・真上・正面を選べる。

配置編集中の家具は左ボタンのドラッグで床に沿って移動する。つかんだ位置を基準に10cmのマス目へ合わせ、立体・真上の視点ではX/Z座標を変える。正面の視点ではX方向だけを動かし、Z座標は維持する。高さ・向き・サイズは変更しない。背景のドラッグと通常の商品画面のドラッグは視点を回転する。Before表示中と、家具を含む完成GLB/GLTFはドラッグ移動の対象外とする。

ドラッグ中は3D上の一時表示だけを動かし、ボタンを離した時点でQueryの部屋データへ反映する。Escapeキーとpointercancelでは元の位置へ戻し、編集履歴にも追加しない。1回のドラッグを履歴1件として扱う。履歴は50件まで保持し、元に戻す・やり直す操作を提供する。「変更を保存」でブラウザに保存する。完成GLB/GLTFの個別移動・回転・色変更は無効にし、理由を表示する。完成モデルでも視点切り替えと商品選択は利用できる。

購入リストCSVは追加商品だけを対象とし、商品名、カテゴリ、幅・高さ・奥行き（cm）、参考価格、ショップ、HTTP/HTTPSの商品リンクを出力する。UTF-8 BOMとCRLFを使い、セルの引用符と数式として解釈される文字を処理する。

## オフライン解析とAPIの商品提案を区別する

オフラインの新規作成は畳数と形だけで部屋の寸法・南側の窓・ベッド・デスク・本棚を返す。fixtureはbackendの `RoomAnalyzer` と同じ生Sceneを作り、APIと共通の変換を使う。希望・スタイル・予算から商品を生成せず、capabilitiesの `coordination` は `false` とする。`demo()`の紫の8商品は参照デザイン確認用に維持する。

正式APIの既定契約は `coordination`。新規作成は部屋解析と商品提案に分け、解析後に活かす家具を選ぶ。結果への追加指示では `backendRoomId` で同じ部屋を再利用し、選択した家具IDも引き継ぐ。新規の初期予算は3万円で、結果の `budget` は正の整数として保存し、再表示時に復元する。backendのモックは希望文のキーワードでテーマを判定し、38件の商品候補から予算と配置場所に収まる商品を選ぶ。写真解析・自然言語を理解するAI・モデル生成は行わない。

商品提案と追加指示には既存家具の最新配置と手動編集した商品の座標・角度・色を `edited_objects` で送る。生成はその配置を考慮し、同じ商品を再採用するときは編集内容を維持する。元の解析SceneはBefore用に保ち、ブラウザには編集記録も保存する。詳細と検証結果は [家具配置の仕様](../furniture-layout/spec.md) を参照する。

開発時は接続設定が未指定ならモックを使い、backendを起動せずに操作できる。開発時だけアカウントメニューに接続切り替えを表示し、選択を `hack.connection.dev` に保存する。本番は常にAPIへ接続し、保存済み接続設定と `VITE_CONNECTION=dummy` を無視する。認証処理と接続先ごとのトークン管理は変更しない。

価格は参考値、購入先はAmazon・楽天市場の商品検索へのリンクとする。結果の `source` は `demo` と `api` を区別し、API接続の結果でもAIによる生成とは表示しない。既存の認証とユーザー管理のRepositoryは維持する。新規登録のパスワードはOpenAPIの8文字以上に合わせる。

ルームはブラウザの `localStorage` の `room-coordinator.plans` に最大30件保存する。以前の `roomie.saved` は使用しない。復元時はDomainの `isRoomDesign` で、必須の文字列、雰囲気と接続元、家具IDの重複、有限の座標、正の寸法、0円以上の有限の価格、HTTP/HTTPSのURLを検証する。不正な保存データは画面へ渡さない。

## 最初のチャットは一項目ずつ入力する

2026年10月4日の追加依頼により、新規ルームの入力を「広さ → 形 → 写真」の順に分ける。各段階では、その項目だけを表示し、進み具合と入力済みの回答を示す。「戻る」で前の段階を修正しても、広さ・形・選んだ写真を保持する。

広さは3〜30畳で、形は既存の3択から選ぶ。写真を受け付ける接続先では、写真の段階を表示する。正式APIの写真は任意で、追加せずに解析へ進める。写真に対応しないオフラインモックでは、形を選んだ後に部屋を表示する。写真は既存の形式・容量・枚数の制限を維持する。

希望と予算は最初の入力から外し、部屋の解析後に活かす家具と一緒に確認する。希望の初期値は空欄とし、既存のスタイル候補からも選べる。解析のRepositoryは希望・予算を必須チェックせず、商品提案時に500文字以内の希望と1円以上の整数の予算を検証する。既存の写真専用契約では「写真 → 希望」の順に分け、写真3〜4枚の必須条件を維持する。

Google Docs URLは未設定のため、今回の依頼と既存API契約を根拠にした。Docsは未確認で、この変更はDocsへ未反映。

## 正式APIを2段階で呼び、Sceneと商品を変換する

`VITE_ROOM_API_CONTRACT` は既定で `coordination`、`analysis` は部屋解析だけ、`legacy` は将来の写真API向け提案形式とする。正式契約はJSON送信で、部屋・商品提案APIは認証必須。環境変数で作成・取得のパスと認証設定を変えられる。このチャットでは公開Swaggerを1時間ごとに監視する設定を追加した。契約が変わっても、未確認のエンドポイントを自動で呼び出さない。

`POST /api/v1/rooms` に `{ room: { tatami, shape } }` を送り、`GET /api/v1/rooms/{id}` の状態が `analyzing` から `ready` になるまで待つ。解析済みの家具を表示し、活かす家具と希望・予算を入力してから商品提案へ進む。

`POST /api/v1/rooms/{id}/coordinations` に `{ coordination: { prompt, budget, kept_object_ids, edited_objects } }` を送る。`kept_object_ids` には選択した解析Sceneの家具IDを指定する。現在のAPIは空配列を全家具の指定として扱うため、家具があるときは全解除で送信できないようにする。`GET /api/v1/coordinations/{id}` が `pending`・`processing` から `done` になるまで待つ。取得は2秒ごと、各処理で最大120秒。失敗・タイムアウト・キャンセルはエラーとして伝え、サンプルへ切り替えない。

backendのSceneは北西の床の角を原点とし、家具位置を底面中心とする。画面の中心座標へ変換するときは、X/Zから部屋の幅・奥行きの半分を引き、Yへ家具の高さの半分を加える。単位はメートル、Y軸が高さ、角度は度。部屋の幅・奥行き・高さ・床色と窓の壁・中心位置・寸法を3Dに反映する。

提案Sceneの `marker` と `item_id` を商品一覧の値と照合し、選択番号・価格・購入リンクを対応させる。`before_scene` は別のスナップショットとして保持し、Before表示に使う。必須項目・状態・商品対応・価格合計が不正な応答はエラーにし、家具や商品の値を補わない。

Domainには `room`、`analysisInput`、`kind`、`backendRoomId`、`before`、`keptObjectIds` を保持する。選択した家具IDは結果と一緒にブラウザへ保存し、追加指示でも再利用する。既存の中心座標・寸法・回転・モデルURL・商品画像も維持し、モデルがない場合は簡易形状で表示する。完成モデルと部屋だけのモデルを区別する `modelKind` も維持する。`legacy` のmultipart形式は正式APIの契約ではなく、写真解析APIの今後の接続用に残す。
